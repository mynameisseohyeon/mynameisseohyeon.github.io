Troubleshooting 1. Schedule–ScheduleTime 부분 저장 방지

Problem

Schedule과 ScheduleTime이 별도 테이블에 저장돼, 한쪽 저장만 성공하면 시간 정보가 없는 불완전한 예약이 남을 수 있었습니다.

Approach

예약 기본 정보와 시간 정보 저장을 하나의 작업으로 보고, 트랜잭션과 Cascade 저장을 적용했습니다.

Action

ScheduleCreateService에 @Transactional을 적용하고, Schedule-ScheduleTime 관계에 CascadeType.ALL과 양방향 연관관계 설정 메서드를 구성했습니다.

Result

저장 과정 중 오류가 발생하면 전체 작업이 롤백되도록 하여 예약 정보와 시간 정보의 부분 저장을 방지했습니다.

Troubleshooting 2. UTC/KST 날짜 경계 불일치 해결

Problem

DB에는 UTC 기준 시간이 저장되고 사용자는 KST 날짜로 조회해, 날짜 경계에서 일부 스케줄이 누락될 수 있었습니다.

Approach

저장 기준은 Instant로 통일하고, 사용자가 선택한 KST 날짜만 UTC Instant 범위로 변환했습니다.

Action

KST 하루 시작과 다음 날 시작을 계산한 뒤 UTC Instant로 변환하고, Repository에서는 [start, end) 반개방 구간으로 조회했습니다.

Result

서버나 DB의 기본 타임존과 관계없이 선택한 KST 날짜의 스케줄을 일관되게 조회할 수 있게 됐습니다.

Troubleshooting 3. 스케줄 목록 멘티 정보 N+1 제거

Problem

DTO 변환 반복문 안에서 멘티 닉네임을 개별 조회해, 목록 크기에 따라 멤버 조회가 반복되는 구조였습니다.

Approach

페이지에 포함된 멘티 ID를 먼저 모으고, 필요한 멤버 정보를 한 번에 조회해 Map으로 재사용했습니다.

Action

menteeId를 distinct()로 정리한 뒤 findAllById()로 일괄 조회하고, DTO 생성 시에는 menteeNicknameMap.get()으로 값을 가져오도록 변경했습니다.

Result

반복 조회를 페이지 단위 일괄 조회로 바꿔, DTO 변환 과정에서 발생하던 추가 Repository 접근을 줄였습니다.

Troubleshooting 4. 예외 응답 표준화

Problem

기능마다 예외를 개별 처리하면 HTTP 상태, 오류 코드, 메시지 형식이 달라져 프론트엔드의 오류 처리 기준이 흔들릴 수 있었습니다.

Approach

ErrorCode Enum으로 도메인 오류를 중앙화하고, 업무 예외와 알 수 없는 서버 예외를 전역 처리기에서 구분했습니다.

Action

@RestControllerAdvice에서 업무 예외는 정의된 상태·코드·메시지로 반환하고, 일반 Exception은 로그 기록 후 고정된 서버 오류 응답으로 분리했습니다.

Result

API 오류 응답을 공통 규격으로 통일해, 클라이언트가 HTTP 상태와 도메인 오류 코드를 기준으로 처리할 수 있게 했습니다.
