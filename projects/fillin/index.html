Technical Challenges

핵심 기술 과제

Challenge 01. 날짜 경계가 어긋나지 않는 일정 조회

Why
사용자는 한국 날짜를 기준으로 캘린더를 조회하지만 저장 값은 UTC 기준 Instant라 자정 전후 일정이 누락될 수 있었습니다.
Decision
LocalDate의 시작과 종료 시점을 Asia/Seoul 기준으로 계산한 뒤 UTC Instant로 변환해 Repository에 전달했습니다.
Result
서버 실행 환경의 기본 시간대에 덜 의존하고, 사용자가 선택한 날짜와 DB 조회 범위를 일치시켰습니다.

Challenge 02. 조회 조건 통합

Why
전체·예정·과거·날짜별 조회가 각각 조건을 처리하면 API가 늘어날수록 수정 범위가 커집니다.
Decision
날짜, 제목, 일정 상태 조건을 정리하는 공통 조회 흐름을 만들고 Pageable 기반 페이지 응답을 유지했습니다.
Result
반복되던 검색 조건 처리를 줄이고, 일정 목록과 캘린더 API의 필터 기준을 같은 방식으로 관리했습니다.

Challenge 03. 예외 응답 표준화

Why
기능마다 예외 응답 형식이 다르면 프론트엔드가 실패 케이스를 화면에 연결하기 어렵습니다.
Decision
BusinessException, ErrorCode, GlobalExceptionHandler 기반으로 공통 오류 응답 구조를 사용했습니다.
Result
에러 코드와 메시지 형식을 통일해 API 문서와 프론트엔드 예외 처리 기준을 맞췄습니다.

Troubleshooting

트러블슈팅

ProblemKST 날짜를 그대로 조회 조건으로 사용하면 UTC 저장 값과 기준이 달라져 선택한 날짜의 일정이 빠질 수 있었습니다.

Action조회 서비스에서 하루의 시작·끝을 Asia/Seoul 기준으로 계산하고 Instant로 변환해 Repository 범위 조건에 전달했습니다.

AlternativeDB 서버의 기본 타임존에 의존하는 방식은 배포 환경이 바뀔 때 같은 문제가 반복될 수 있어 배제했습니다.

Result사용자 날짜 기준과 저장 시간 기준을 명확히 분리해 캘린더 조회의 날짜 경계 오류 가능성을 줄였습니다.

ProblemSchedule 저장 후 ScheduleTime 저장이 실패하면 시간 정보가 없는 불완전한 예약 데이터가 남을 수 있었습니다.

Action예약 생성 로직에 @Transactional을 적용해 두 테이블 저장을 하나의 작업 단위로 묶었습니다.

Alternative실패 시 수동 삭제하는 방식은 예외 경로가 늘어날수록 누락 위험이 커진다고 판단했습니다.

Result저장 과정 중 하나라도 실패하면 전체 롤백되도록 구성해 예약 정보와 수업 시간의 정합성을 확보했습니다.

Retrospective

한계와 개선 방향

일정 조회는 단순 목록 조회처럼 보이지만, 실제로는 사용자 역할, 일정 상태, 날짜 경계, 페이지네이션이 함께 엮이는 도메인이라는 점을 배웠습니다. 다음 단계에서는 동시 예약 상황의 충돌 방지와 결제 승인 이후 상태 전이를 더 세밀하게 검증하고, 조회 조건이 늘어나도 정책을 안정적으로 확장할 수 있도록 테스트 케이스를 보강하고 싶습니다.
