조회에서 실제 방문까지 이어지도록 설계한 관광 서비스입니다.

Overview

문제, 기여, 결과

Problem관광지 조회에서 끝나는 서비스는 실제 방문과 재방문 동기를 만들기 어렵습니다.

My Contribution미션 검증 정책, 사용자별 완료 이력, 보상 저장 흐름, 관광 데이터 수집 구조를 설계했습니다.

Key Challenge퀴즈, 걸음 수, 사진, QR처럼 기준이 다른 미션을 하나의 완료 정책으로 다루는 것이 핵심이었습니다.

Outcome미션 유형 추가 시 기존 완료 이력 정책을 유지하고, 중복 요청에서도 이력이 1건만 남도록 설계했습니다.

Architecture

도메인 중심 구조와 데이터 변경 이력 관리

앱은 Flutter 클라이언트에서 Spring Boot API로 요청하고, 관광지·미션·보상 이력은 PostgreSQL에 저장합니다. 관광 데이터는 TourAPI와 Kakao Local을 통해 수집하며, Redis는 반복 조회가 많은 데이터의 캐싱 지점으로 고려했습니다.

Technical Challenges

기술적 판단

Challenge 01. 미션 유형별 검증 구조

Why
미션 유형마다 검증 입력과 성공 조건이 달라 if 분기가 늘어날 가능성이 컸습니다.
Decision
미션 유형과 검증 기준을 정책으로 분리해 신규 유형 추가 시 기존 완료 흐름 변경을 줄였습니다.
Result
퀴즈, 걸음 수, 사진, QR 검증을 동일한 완료 요청 흐름 안에서 다룰 수 있게 했습니다.

Challenge 02. 중복 완료 및 보상 방지

Why
네트워크 재시도나 중복 클릭으로 동일 미션 완료 요청이 반복될 수 있었습니다.
Decision
사용자·미션 조합을 기준으로 완료 이력과 보상 이력을 분리하고 중복 저장을 제한했습니다.
Result
반복 요청에서도 완료 이력과 보상 이력이 각각 1건만 남도록 데이터 흐름을 정리했습니다.

Challenge 03. 외부 관광 데이터 정제

Why
외부 API 응답에는 좌표 누락, 카테고리 차이, 지역 표기 불일치가 섞일 수 있습니다.
Decision
서비스에서 필요한 좌표, 지역, 카테고리 값을 중심으로 저장 전 정규화 단계를 두었습니다.
Result
지도 표시와 지역별 탐색에서 사용할 수 있는 형태로 관광지 데이터를 관리했습니다.

PAAR

반복 요청에서도 미션 완료 이력 1건 유지

Problem사용자가 같은 미션을 여러 번 완료 요청하면 보상이 중복 지급될 수 있습니다.

Action완료 상태를 먼저 조회하고, 저장 시 사용자·미션 기준으로 중복 생성을 차단했습니다.

Alternative프론트엔드 버튼 비활성화만으로 막는 방식은 재요청과 네트워크 재시도에 취약하다고 판단했습니다.

Result동일 사용자·미션 반복 요청에서도 완료 이력과 보상 이력이 각각 1건만 생성되는 흐름을 만들었습니다.

Testing

검증 결과

테스트 케이스기대 결과확인 결과
동일 미션 반복 완료 요청완료 이력과 보상 이력이 각각 1건만 유지서비스 로직 기준 통과
필수 좌표가 없는 관광 데이터지도 표시 대상에서 제외 또는 저장 전 검증샘플 데이터 기준 확인
Flyway 마이그레이션 재실행로컬과 배포 DB 스키마를 동일하게 재현마이그레이션 순서 확인

Retrospective

회고와 개선 방향

현재 중복 방지는 DB 제약조건과 서비스 선검증을 중심으로 처리했습니다. 이후 트래픽이 늘어나면 같은 사용자 요청이 짧은 시간에 몰릴 수 있으므로, 요청 멱등키와 락 전략을 비교해 보상 지급 흐름을 개선할 계획입니다. 또한 관리자 화면에서 미션 정책을 직접 조정할 수 있게 만들어 운영자가 코드 수정 없이 이벤트를 확장할 수 있도록 발전시키고 싶습니다.
