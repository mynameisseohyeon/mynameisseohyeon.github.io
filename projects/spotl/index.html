Overview

운영자가 관리 가능한 공연 예약 서비스

기간2024.09 - 2024.12

역할Backend Developer / Product Owner

핵심 스택Java 17, Spring Boot 3.3, JPA, MySQL, AWS S3

문서화Swagger 기반 API 테스트 및 문서 조회

공연 정보와 예약 현황이 분산되어 관리되는 문제를 해결하기 위해 공연 등록, 예약, 관리자 승인, QR 입장 확인을 연결했습니다. 백엔드에서는 예약 중복 방지, 공연 공개 상태, 사용자 인증, 입장 검증 흐름을 담당했습니다.

Architecture

역할별 API와 외부 서비스 연동

일반 사용자, 공연 주최자, 관리자 역할을 나누고 각 역할의 API 접근 범위를 분리했습니다. 공연 포스터는 S3에 저장하고, SMS 본인 인증과 지도 API를 외부 서비스로 연동했습니다.

Technical Challenges

핵심 기술 문제

예약 중복 방지

동일 사용자가 취소되지 않은 예약을 중복 생성하지 않도록 예약 생성 전 조건 조회를 수행했습니다.

공연 공개 정책

관리자 승인 상태에 따라 사용자에게 노출되는 공연을 제한해 운영 품질을 관리했습니다.

QR 입장 검증

예약자 정보와 QR 인식 결과를 연결해 현장 입장 여부를 빠르게 확인하는 흐름을 구성했습니다.

PAAR

예약 생성 로직의 안정성

Problem공연 예약은 중복 생성되면 좌석·입장 관리가 흔들리고 운영자가 수동으로 정리해야 합니다.

Decision예약 생성 전에 공연 존재 여부, 사용자 존재 여부, 취소되지 않은 기존 예약을 순서대로 검증했습니다.

Implementation조회 로직을 분리해 조건별 예약 목록과 단건 조회를 명확히 나누고, API 응답 형식을 통일했습니다.

Result예약 생성 흐름의 예외 조건이 명확해지고, 프론트엔드와 API 계약을 안정적으로 맞출 수 있었습니다.

Testing

검증 방식

  • Swagger에서 공연 생성, 예약 생성, SMS 인증 API의 요청·응답을 반복 확인
  • 취소되지 않은 예약이 있는 사용자의 중복 예약 요청을 예외 케이스로 검증
  • 공연 승인 상태에 따라 목록 노출 여부가 달라지는지 시나리오 기반 확인

Retrospective

회고와 개선 방향

예약과 입장 관리처럼 운영 리스크가 큰 도메인은 예외 조건을 먼저 명확히 해야 한다는 점을 배웠습니다. 이후에는 동시 예약 상황의 트랜잭션 격리와 부하 테스트를 추가해 더 높은 안정성을 검증하고 싶습니다.
