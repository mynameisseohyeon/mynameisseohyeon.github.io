Technical Challenges

기술적 판단

Challenge 01. 예약 중복 방지

Why
동일 사용자가 같은 공연을 여러 번 예약하면 현장 입장과 예약자 통계가 흔들립니다.
Decision
예약 생성 전에 공연 존재 여부, 사용자 존재 여부, 취소되지 않은 기존 예약을 순서대로 검증했습니다.
Result
중복 예약 예외 조건이 명확해져 프론트엔드가 사용자에게 같은 형식의 실패 응답을 보여줄 수 있었습니다.

Challenge 02. 공연 승인 정책

Why
등록된 모든 공연을 즉시 공개하면 부정확한 정보가 사용자에게 노출될 수 있습니다.
Decision
관리자 승인 상태를 공연 목록 조회 조건에 포함해 승인된 공연만 공개되도록 분리했습니다.
Result
운영자가 공연 품질을 확인한 뒤 사용자에게 노출하는 흐름을 만들었습니다.

Challenge 03. API 계약 일관성

Why
기능별 응답 형식이 달라지면 프론트엔드 예외 처리 비용이 커집니다.
Decision
data, message, code 형식의 공통 응답을 적용하고 Swagger에서 요청·응답을 반복 확인했습니다.
Result
성공과 실패 응답의 모양이 통일되어 기능 연결과 디버깅이 쉬워졌습니다.

Troubleshooting

문제, 분석, 적용, 결과

01. 중복 예약 검증

문제
동일 사용자가 같은 공연을 반복 예약하면 예약자 수와 현장 입장 데이터가 흔들릴 수 있었습니다.
분석
예약 생성 시 공연, 사용자, 기존 예약 상태를 한 흐름에서 확인해야 했습니다.
적용
예약 생성 전에 공연 존재 여부, 사용자 존재 여부, 취소되지 않은 예약을 순서대로 검증했습니다.
결과
중복 예약 예외를 명확히 반환하고 프론트엔드가 같은 형식으로 실패 응답을 처리할 수 있게 했습니다.

02. 공연 공개 승인 흐름

문제
등록된 공연이 즉시 공개되면 검수되지 않은 정보가 사용자에게 노출될 수 있었습니다.
분석
공연 등록과 사용자 목록 조회 사이에 관리자 승인 상태가 필요했습니다.
적용
승인 상태를 공연 조회 조건에 포함하고, 관리자 승인 후에만 사용자에게 노출되도록 분리했습니다.
결과
운영자가 공연 정보를 확인한 뒤 공개하는 흐름을 만들었습니다.

03. API 응답 형식 통일

문제
기능마다 응답 구조가 달라지면 프론트엔드 예외 처리와 디버깅 비용이 커질 수 있었습니다.
분석
성공, 실패, 검증 오류를 같은 응답 틀에서 해석할 수 있어야 했습니다.
적용
data, message, code 형식의 공통 응답을 적용하고 Swagger로 요청·응답을 반복 확인했습니다.
결과
기능 연결 과정에서 응답 해석이 쉬워지고 오류 처리 기준이 명확해졌습니다.

PAAR

예약 생성 로직의 안정성

Problem예약 생성은 공연 존재, 사용자 상태, 중복 예약 여부가 모두 맞아야 성공할 수 있습니다.

Action조건별 조회와 검증 순서를 서비스 레이어에 모아 예약 생성 전 실패 조건을 먼저 반환했습니다.

Alternative컨트롤러에서 조건을 직접 처리하는 방식은 기능이 늘어날수록 중복 코드가 커진다고 판단했습니다.

Result예약 검증 정책을 독립적으로 수정할 수 있게 되었고 API 응답 계약도 안정적으로 유지했습니다.

Retrospective

회고와 개선 방향

예약과 입장 관리처럼 운영 리스크가 큰 도메인은 예외 조건을 먼저 명확히 해야 한다는 점을 배웠습니다. 현재는 기능별 API 검증 중심으로 안정성을 확인했지만, 이후에는 동시 예약 상황의 트랜잭션 격리와 부하 테스트를 추가해 실제 공연 오픈 시점의 요청 집중 상황까지 검증하고 싶습니다.
